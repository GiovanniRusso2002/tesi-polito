\chapter{Architecture and Design}
\label{chap:architecture}

This chapter presents the architectural design of the modernized cloud infrastructure, explaining the design decisions, trade-offs, and rationale behind the proposed solution. We adopt a systematic approach, starting from high-level system architecture and progressively detailing individual components.

    \item Modernized file-sharing service
    \item User management service
    \item Configuration synchronization service
    \item Storage backend (object storage)

\section{Design Principles}
The architecture is guided by the following principles:
\begin{itemize}
    \item \textbf{Security by design:} All services use OIDC for authentication; sensitive data is encrypted in transit and at rest.
    \item \textbf{Scalability:} Stateless service design enables horizontal scaling.
    \item \textbf{Resilience:} Health checks, automatic restarts, and graceful degradation ensure high availability.
    \item \textbf{Maintainability:} Clear separation of concerns, modular design, and comprehensive documentation.
    \item \textbf{Cloud-native:} Leverages Kubernetes-native abstractions and follows the twelve-factor app methodology.
\end{itemize}

\section{Authentication and Authorization Flow}
\subsection{OIDC Integration Architecture}
We describe the end-to-end authentication flow:
\begin{enumerate}
    \item User initiates login via frontend or API client
    \item Request is redirected to Keycloak authorization endpoint
    \item User authenticates with Keycloak
    \item Keycloak issues authorization code
    \item Client exchanges code for access and refresh tokens
    \item Access token is included in subsequent API requests
    \item Services validate tokens with Keycloak's public key
\end{enumerate}

\subsection{Authorization Model}
We employ role-based access control (RBAC) with the following roles:
\begin{itemize}
    \item \textbf{Admin:} Full access to all resources and configuration
    \item \textbf{User:} Access to own files and shared resources
    \item \textbf{Guest:} Limited read-only access to public resources
\end{itemize}

Token claims encode user roles, which are validated at the service level to enforce access policies.

\section{File-Sharing Service Architecture}
\subsection{Service Components}
The file-sharing service consists of:
\begin{itemize}
    \item \textbf{API layer:} RESTful endpoints for upload, download, delete, and share operations
    \item \textbf{Authentication middleware:} Validates OIDC tokens
    \item \textbf{Authorization layer:} Enforces access control policies
    \item \textbf{Storage abstraction:} Interfaces with object storage backend
    \item \textbf{Metadata service:} Manages file metadata and sharing permissions
\end{itemize}

\subsection{Storage Backend}
We use object storage (MinIO or cloud-native S3) for file persistence. File paths are structured as:
\begin{verbatim}
/<user-id>/<file-id>/<filename>
\end{verbatim}

Access to storage is mediated through signed URLs or service-level permissions, ensuring users cannot bypass application-level access control.

\subsection{Sharing Mechanisms}
Two sharing models are supported:
\begin{itemize}
    \item \textbf{User-to-user:} Direct sharing via user ID
    \item \textbf{Link-based:} Temporary shareable links with expiration
\end{itemize}

Sharing metadata is stored in a relational database, indexed by file ID and user ID for efficient query performance.

\section{User Management Service}
The user management service acts as a bridge between the application and Keycloak:
\begin{itemize}
    \item User registration and profile management
    \item Role assignment and permission updates
    \item Audit logging of user actions
\end{itemize}

It uses Keycloak's Admin API to synchronize user data and roles.

\section{Configuration Synchronization Service}
The configuration synchronization service manages deployment configurations across multiple environments (development, staging, production).

\subsection{Design Goals}
\begin{itemize}
    \item Centralized configuration source of truth (Git repository)
    \item Automated propagation of configuration changes
    \item Conflict detection and resolution strategies
    \item Rollback capabilities for failed deployments
\end{itemize}

\subsection{Architecture}
The service monitors a Git repository for configuration changes, validates changes against predefined schemas, and applies updates to target Kubernetes clusters using Helm or kubectl.

\section{Networking and Communication}
\subsection{Service Discovery}
Kubernetes Services provide internal DNS-based service discovery. External access is handled by Ingress controllers with TLS termination.

\subsection{Inter-Service Communication}
Services communicate via RESTful APIs over HTTP/2. Authentication between services uses service accounts with JWT tokens issued by Keycloak.

\subsection{Network Policies}
Kubernetes NetworkPolicies restrict traffic to minimize attack surface:
\begin{itemize}
    \item File-sharing service can only receive traffic from Ingress
    \item Database access is restricted to authorized services
    \item External egress is limited to necessary endpoints (Keycloak, object storage)
\end{itemize}

\section{Security Architecture}
\subsection{Defense in Depth}
Multiple security layers:
\begin{itemize}
    \item TLS for all external and internal communication
    \item Token-based authentication with short-lived access tokens
    \item Principle of least privilege for service accounts
    \item Regular security audits and vulnerability scanning
\end{itemize}

\subsection{Secrets Management}
Sensitive data (API keys, database passwords, TLS certificates) is stored in Kubernetes Secrets with encryption at rest enabled.

\section{Monitoring and Observability Architecture}
\subsection{Metrics Collection}
Each service exposes Prometheus-compatible metrics on a dedicated endpoint. Key metrics include request latency, error rates, and authentication success/failure counts.

\subsection{Distributed Tracing}
We implement distributed tracing using OpenTelemetry to track request flows across services, enabling root cause analysis of performance bottlenecks.

\subsection{Alerting}
Prometheus AlertManager sends notifications for critical events:
\begin{itemize}
    \item Service downtime
    \item High error rates
    \item Resource exhaustion (CPU, memory, disk)
    \item Failed authentication attempts exceeding threshold
\end{itemize}

\section{Design Decisions and Trade-offs}
We explicitly document key design decisions and their trade-offs:

\subsection{Choice of Keycloak over Alternatives}
\textbf{Alternatives considered:} Auth0, Okta, custom JWT solution  
\textbf{Decision:} Keycloak  
\textbf{Rationale:} Open-source, self-hosted, no vendor lock-in, comprehensive OIDC support  
\textbf{Trade-off:} Increased operational overhead for self-hosting

\subsection{Object Storage over File System}
\textbf{Alternatives considered:} Shared NFS, distributed file systems (Ceph)  
\textbf{Decision:} Object storage (S3-compatible)  
\textbf{Rationale:} Cloud-native, scalable, integrates with existing infrastructure  
\textbf{Trade-off:} Slightly higher latency for small file access

\subsection{Synchronous vs. Asynchronous Configuration Updates}
\textbf{Decision:} Synchronous updates with rollback mechanism  
\textbf{Rationale:} Immediate feedback on configuration errors, simpler debugging  
\textbf{Trade-off:} Slower for large-scale updates, blocks on failures

\section{Scalability and Performance Considerations}
The architecture supports horizontal scaling of stateless services. We identify potential bottlenecks:
\begin{itemize}
    \item Database connections (addressed via connection pooling)
    \item Token validation overhead (mitigated by caching public keys)
    \item Object storage I/O (managed via CDN for frequently accessed files)
\end{itemize}

\section{Summary}
This chapter presented a comprehensive architectural design for the modernized cloud infrastructure. We detailed component interactions, security mechanisms, and design trade-offs. The next chapter describes the implementation of this architecture.
