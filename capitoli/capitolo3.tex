\chapter{Case Study Baseline (As-Is System)}
\label{chap:baseline}

This chapter describes the initial state of the Outsight Cloud platform before the migration design was formalized. The goal is to establish the baseline against which migration decisions are evaluated.

\section{Current Architecture and Data Flow}
The as-is platform handled LiDAR-related assets and simulations through a web application and backend API stack:
\begin{itemize}
    \item Frontend based on Vue 3.
    \item Backend based on Node.js/Express.
    \item Redis-backed session mechanisms.
    \item Containerized deployment with reverse-proxy routing.
    \item File storage through S3-compatible object storage services.
    \item Core business data strongly coupled to Airtable.
\end{itemize}

This architecture enabled fast delivery in earlier stages of product evolution, but it created a concentration of dependencies in external data services and manually maintained infrastructure conventions.

\section{Airtable as Primary Data Storage}
Before the migration to PostgreSQL, Outsight Cloud relied on Airtable as its primary data storage system. Airtable acted not only as a database, but also as an operational platform supporting multiple workflows inside the application domain.

It stored core entities such as users, organizations, sites, simulations, role assignments, and permissions. In addition, Airtable was used for operational forms and for triggering integrations with external services, including Slack notifications.

Unlike a traditional relational DBMS, Airtable organizes data through linked records and lookup fields. This model offered flexibility in the early product phase and enabled rapid prototyping, especially because non-technical stakeholders could inspect and manipulate data through a graphical interface.

\section{Limitations of Airtable}
As the platform evolved and the amount of managed data increased, several limitations became evident.

\subsection{Data Modeling and Consistency}
Relationships between entities (for example organizations, sites, and simulations) were represented through linked records and lookup fields, rather than enforced through explicit foreign-key constraints. As a consequence, consistency guarantees depended heavily on application logic.

During access and synchronization flows, lookup fields could expose heterogeneous representations of the same logical information. In some contexts values appeared as scalars, while in others they appeared as arrays. This increased backend complexity and made query and mapping logic harder to maintain.

\subsection{Limited Relational Capabilities}
Airtable does not provide full relational capabilities comparable to SQL databases. Advanced joins, complex filtering patterns, indexing strategies, and transactional control are more limited than in PostgreSQL-like systems.

\subsection{Operational Inefficiency}
Several workflows depended on manual interactions through Airtable forms. In particular, user creation and onboarding required internal manual intervention, which slowed operations and increased the probability of human error.

\subsection{Scalability, Coupling, and Cost}
Over time, Airtable became both application datastore and operational control surface. This created tight coupling between business logic and Airtable-specific concepts, increasing technical debt and reducing architectural evolvability.

The economic impact was also significant: recurring operational costs reached approximately EUR~1000 per month for database usage alone.

\section{Motivation for Migration to PostgreSQL}
The migration to PostgreSQL was initiated to address these constraints and provide a more robust foundation for the future evolution of Outsight Cloud.

PostgreSQL introduced key advantages:
\begin{itemize}
    \item explicit relational modeling through primary and foreign keys;
    \item stronger guarantees for data consistency and integrity;
    \item improved querying capabilities and indexing mechanisms;
    \item reduced dependence on Airtable-specific structures;
    \item lower operational cost exposure;
    \item improved scalability and maintainability.
\end{itemize}

The migration also aligned with the broader cloudification strategy and AWS replatforming effort aimed at long-term reliability and maintainability.

Therefore, the objective was not only to replace one storage technology with another, but to progressively transition from a semi-structured operational backend to a maintainable and scalable relational architecture.
