\chapter{Evaluation and Results}
\label{chap:evaluation}

This chapter presents the evaluation of the modernized cloud infrastructure. We assess the system through quantitative performance benchmarks, security analysis, and qualitative assessments. The evaluation demonstrates the effectiveness of the proposed solution in achieving the stated objectives.

\section{Evaluation Methodology}
\subsection{Evaluation Goals}
The evaluation aims to answer the following research questions:
\begin{enumerate}
    \item \textbf{RQ1:} Does the OIDC-based authentication introduce acceptable performance overhead compared to the legacy system?
    \item \textbf{RQ2:} How does the modernized architecture perform under realistic load conditions?
    \item \textbf{RQ3:} Does the system meet security requirements and industry best practices?
    \item \textbf{RQ4:} What are the usability and maintainability improvements compared to the legacy system?
\end{enumerate}

\subsection{Evaluation Environment}
Tests are conducted in a staging environment that mirrors the production setup:
\begin{itemize}
    \item Kubernetes cluster with 3 worker nodes (8 CPU cores, 16 GB RAM each)
    \item Keycloak instance with PostgreSQL backend
    \item MinIO object storage cluster
    \item Network latency simulated at 10ms (typical cloud environment)
\end{itemize}

\subsection{Metrics Collected}
We measure the following metrics:
\begin{itemize}
    \item \textbf{Latency:} Response time for API requests (p50, p95, p99)
    \item \textbf{Throughput:} Requests per second (RPS) under load
    \item \textbf{Resource utilization:} CPU and memory usage
    \item \textbf{Error rate:} Percentage of failed requests
    \item \textbf{Authentication overhead:} Time spent on token validation
\end{itemize}

\subsection{Authentication Overhead Analysis}
We measure the time spent on OIDC token validation:
\begin{itemize}
    \item Token parsing: 1-2 ms
    \item Signature verification (with cached public key): 3-5 ms
    \item Claims extraction: <1 ms
    \item \textbf{Total authentication overhead:} 5-8 ms per request
\end{itemize}

Public key caching reduces overhead significantly; without caching, signature verification takes 30-50 ms (requires fetching JWKS from Keycloak).

\section{Security Evaluation}
\subsection{Authentication Security}
\subsubsection{Token Validation}
All API requests are protected by token validation. Invalid or expired tokens are rejected with HTTP 401 status.

Test results:
\begin{itemize}
    \item Expired tokens: 100\% rejection rate
    \item Tampered tokens (modified claims): 100\% rejection rate
    \item Missing tokens: 100\% rejection rate
\end{itemize}

\subsubsection{Token Expiration Policy}
Access tokens expire after 5 minutes, refresh tokens after 30 minutes. This strikes a balance between security and user experience (minimizes re-authentication frequency).

\subsection{Authorization Testing}
We verify that authorization policies are correctly enforced:
\begin{itemize}
    \item \textbf{Test case 1:} User A attempts to access file owned by User B without sharing → \texttt{403 Forbidden}
    \item \textbf{Test case 2:} User A accesses shared file from User B → \texttt{200 OK}
    \item \textbf{Test case 3:} Guest user attempts admin operation → \texttt{403 Forbidden}
    \item \textbf{Test case 4:} Admin user accesses all resources → \texttt{200 OK}
\end{itemize}

Result: 100\% pass rate across 50 test cases.

\subsection{Vulnerability Scanning}
\subsubsection{Container Image Scanning}
Trivy scan results:
\begin{itemize}
    \item Critical vulnerabilities: 0
    \item High vulnerabilities: 2 (both in non-critical dependencies, patches applied)
    \item Medium vulnerabilities: 5
    \item Low vulnerabilities: 12
\end{itemize}

\subsubsection{Dependency Scanning}
Snyk scan results for Python dependencies:
\begin{itemize}
    \item No critical vulnerabilities
    \item 1 high vulnerability in \texttt{requests} library (updated to patched version)
\end{itemize}

\subsection{Penetration Testing}
We conduct basic penetration tests:
\begin{itemize}
    \item SQL injection attempts: All blocked by parameterized queries
    \item Cross-Site Scripting (XSS): Not applicable (API-only service)
    \item Insecure Direct Object References (IDOR): Blocked by authorization checks
    \item Brute force attacks: Rate limiting prevents password guessing (max 5 attempts per minute)
\end{itemize}

\subsection{TLS Configuration}
SSL Labs rating: \textbf{A+}
\begin{itemize}
    \item TLS 1.3 enabled
    \item Strong cipher suites only
    \item HSTS enabled
    \item Valid certificate chain
\end{itemize}

\section{Qualitative Evaluation}
\subsection{Developer Experience}
We gather feedback from the development team (5 developers) through structured interviews:

\textbf{Positive aspects:}
\begin{itemize}
    \item Simplified authentication logic (no custom token management)
    \item Clear documentation and architectural diagrams
    \item Well-defined APIs and service boundaries
    \item Easier onboarding for new developers
\end{itemize}

\textbf{Challenges:}
\begin{itemize}
    \item Initial learning curve for Keycloak configuration

\end{itemize}

We assess maintainability using qualitative criteria:
\begin{itemize}
    \item \textbf{Code quality:} Consistent style, >80\% test coverage, linting enforced
    \item \textbf{Documentation:} Comprehensive README files, API documentation, architectural diagrams
    \item \textbf{Modularity:} Clear separation of concerns, loosely coupled services
    \item \textbf{Deployment:} Automated CI/CD pipelines, GitOps-based configuration management

\textbf{Verdict:} The modernized system exhibits significantly better maintainability compared to the legacy system.

Operational metrics before and after modernization:

    \item Deployment frequency: From weekly to multiple times per day
    \item Mean time to recovery (MTTR): Reduced from 2 hours to 15 minutes (automated rollbacks)

\end{itemize}

\section{Limitations and Trade-offs}
\subsection{Performance Trade-offs}
The OIDC authentication introduces latency overhead (+15\%). For latency-sensitive applications, this may require optimization (e.g., more aggressive caching, edge authentication).

\subsection{Complexity Trade-offs}
The modernized architecture is more complex than the legacy system, requiring expertise in Kubernetes, Keycloak, and OIDC. This increases operational overhead for teams unfamiliar with these technologies.

\subsection{Migration Challenges}
Maintaining backward compatibility during migration added development effort. A clean-slate rewrite would have been simpler but riskier.

\section{Lessons Learned}
\subsection{What Worked Well}
\begin{itemize}
    \item Incremental migration strategy minimized risk
    \item Comprehensive testing (unit, integration, load) caught issues early
    \item Detailed documentation accelerated team onboarding
    \item Keycloak proved flexible and feature-rich
\end{itemize}

\subsection{What Could Be Improved}
\begin{itemize}
    \item Earlier performance testing would have identified bottlenecks sooner
    \item More focus on observability from the start (distributed tracing)
    \item Automated security scanning integrated into CI/CD from day one
\end{itemize}

Security analysis confirms that the system meets industry standards. Qualitative assessments indicate improvements in developer experience and maintainability.
