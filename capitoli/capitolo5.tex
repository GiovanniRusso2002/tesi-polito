\chapter{Target Architecture and Solution Design (To-Be)}
\label{chap:architecture}

This chapter presents the target architecture resulting from the decision framework in Chapter~\ref{chap:methodology}. The architecture is described as a migration destination designed for incremental adoption.

\section{Architecture Overview}
The target architecture is organized around four concerns:
\begin{itemize}
    \item \textbf{Application runtime:} containerized frontend and backend services deployed on managed cloud compute.
    \item \textbf{Traffic and exposure:} explicit HTTP routing and health endpoints through managed load balancing.
    \item \textbf{Persistence and assets:} relational persistence for business data and object storage for simulation files.
    \item \textbf{Operations:} IaC-controlled provisioning, log collection, and environment-specific governance.
\end{itemize}

\section{Identity, Data, and Storage Design}
\subsection{Identity Design Direction}
The target identity direction is standards-based and service-oriented. Authentication and authorization concerns are progressively decoupled from application-specific legacy assumptions, enabling future CIAM/SSO integration while preserving migration continuity.

\subsection{Data-Layer Design Direction}
The data architecture moves from Airtable-centric coupling toward PostgreSQL-based persistence under explicit schema control. Migration is designed as incremental coexistence, supported by replication and validation tooling.

\subsection{Storage Design}
Simulation and file assets are maintained in private object storage with CDN distribution where required. Access patterns are controlled through IAM-based permissions and bounded service responsibilities.

\section{Security, Observability, and Deployment Design}
\subsection{Security Design}
Security decisions prioritize:
\begin{itemize}
    \item least-privilege access policies for services and automation;
    \item secrets handling through managed secret services;
    \item explicit separation between public entry points and internal service surfaces.
\end{itemize}

\subsection{Observability Design}
The target architecture includes centralized operational visibility through managed logging and monitoring services. This is essential for migration because it provides evidence during coexistence and switchover phases.

\subsection{Deployment Design}
Deployment design is Terraform-driven, with explicit environment separation and reviewable infrastructure changes. This addresses reproducibility and reduces configuration drift across stages.

\section{Design Decisions and Trade-offs}
The final architecture reflects trade-offs rather than absolute optimization:
\begin{itemize}
    \item managed services reduce platform maintenance effort but introduce configuration discipline requirements;
    \item incremental migration reduces cutover risk but increases temporary system complexity;
    \item coexistence validation improves confidence but requires dedicated testing and data checks.
\end{itemize}

Overall, the chosen design prioritizes migration safety and long-term maintainability over short-term simplification.
